# Лабораторна робота №5: Просунуті запити (Фільтрація, Пагінація, Ролі)

## 1. Мета роботи
Опанувати обробку параметрів запиту (Query Parameters) для реалізації фільтрації та пагінації (сторінкового виводу) даних у REST API. Навчитися реалізовувати рольову модель доступу (RBAC — Role-Based Access Control) для розмежування прав звичайних користувачів та адміністраторів.

## 2. Теоретичні відомості
- **Query Parameters (Параметри запиту)** — частина URL-адреси, яка йде після знаку питання `?` та використовується для передачі додаткових налаштувань запиту (наприклад, `/api/places?city=Київ`). В Express доступні через об'єкт `req.query`.
- **Пагінація (Pagination)** — процес розділення великого масиву даних на менші порції (сторінки) для зменшення навантаження на сервер та мережу. Найпопулярніший підхід: використання параметрів `limit` (кількість записів на сторінку) та `offset` або `page` (номер сторінки або зміщення).
- **Фільтрація** — відбір записів з бази даних за певними критеріями (наприклад, пошук локацій лише з певного міста).
- **RBAC (Role-Based Access Control)** — підхід до управління доступом, де права прив'язані до ролей (наприклад, `user`, `admin`), а користувачам призначаються ці ролі.
- **Role Middleware** — проміжна функція, яка викликається після Auth Middleware, перевіряє роль авторизованого користувача (`req.user.role`) та приймає рішення про допуск до певного маршруту.

## 3. Завдання
1. Модифікувати ендпоінт `GET /api/places` для підтримки пагінації. Додати обробку query-параметрів `page` (за замовчуванням 1) та `limit` (за замовчуванням 10).
2. Реалізувати фільтрацію для `GET /api/places`. Додати можливість пошуку за параметром `city` (точний збіг або частковий — `ILIKE`/`LIKE`).
3. (Опціонально) Додати розрахунок та вивід загальної кількості записів та сторінок у відповідь (метадані пагінації).
4. Написати `roleMiddleware(allowedRoles)`, який буде експортувати функцію, здатну перевіряти, чи входить роль поточного користувача в масив дозволених ролей.
5. Розширити логіку видалення та оновлення місць (`DELETE /api/places/:id` та `PUT /api/places/:id`), а також відгуків: тепер адміністратори (`role: 'admin'`) можуть видаляти або редагувати БУДЬ-ЯКЕ місце чи відгук, незважаючи на те, що воно їм не належить.
6. Протестувати нові функції через Postman, створивши користувача з роллю `admin` (напряму в БД або через спеціальний прихований ендпоінт).


### 4.2. API Endpoints
- `GET /api/places?page=1&limit=5&city=Київ`
  - *Response:*
```json
  {
      "success": true,
      "data": [
        { /* місце 1 */ },
        { /* місце 2 */ }
      ],
      "meta": {
        "total": 24,
        "page": 1,
        "limit": 5,
        "totalPages": 5
      }
  }
```

- `DELETE /api/places/:id`
    - *Behavior:*
        - Якщо користувач має роль `user` і не є власником місця, повертається `403 Forbidden`.
        - Якщо користувач має роль `admin`, він може видалити будь-яке місце незалежно від власності.

## 5. Очікуваний результат
1. При запиті до `GET /api/places` без параметрів повертається перша сторінка (наприклад, 10 локацій).
2. При додаванні параметра `?city=Львів` повертаються локації лише з цього міста.
3. Користувач з роллю `user` отримує `403 Forbidden` при спробі видалити чужий запис.
4. Користувач з роллю `admin` успішно видаляє будь-який запис у системі.
